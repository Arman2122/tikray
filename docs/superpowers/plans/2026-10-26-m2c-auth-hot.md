# M2c: sign-in and hot changes Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** People can sign in to `tikray serve` with a password, and server changes can go live without restarting xray.
- **Sign-in:** the first admin is claimed with a one-time setup code. Passwords are hashed with argon2id. Browser sessions use secure cookies with CSRF protection, sign-in attempts are rate limited, and the admin can create named API tokens for scripts.
- **Hot changes:** a change that only adds, removes or edits servers is applied through `xray api` without a restart. Anything else, or a hot change that fails, takes the full trial as in M2b.
- **M2b carries:** servers saved untested are re-tested once a core runs, and per-server tests are batched.
- Everything is proven end to end on RouterOS CHR.

**Architecture:**
- **`internal/auth` (new):** the admin account, sessions, API tokens, the setup code, CSRF and the rate limiter. They are kept in `<data>/state/auth.json`, apart from the desired state, which is rendered and exported.
- **`internal/api`:** its authentication becomes a chain:
  1. the M2b bearer token (`api.token`, now called the *root token*: the in-container CLI and the installer use it);
  2. named API tokens;
  3. session cookies, where any request that isn't GET or HEAD also needs the CSRF header.
- **Hot changes:** they live in `internal/artifacts`, next to the trial, under the same lock. The runner gains `POST /v1/adopt`, which makes a config active without a restart.
- **The service** keeps calling `Apply`; artifacts decides between hot and trial.
- **Rule edits stay trials.** §3.4 also lists rule edits (`adrules`/`rmrules`), but xray's `adrules` only appends and rules are order-sensitive, so a hot rule edit can't reproduce the rendered order. Rule edits stay on the trial, and the spec update says so.

**Tech Stack:** Go 1.24, the stdlib, and `golang.org/x/crypto/argon2` (`x/crypto` is already a dependency). No other new dependency. The lab is M0–M2b's `test/lab` and `test/e2e`.

**Spec:** `docs/superpowers/specs/2026-10-24-tikray-design.md`, §3.4 (hot changes, M2c), §3.5, §6.1 (the setup code the installer shows), §7 and §10.

## Global Constraints

- Everything in M2b's Global Constraints still holds. In particular:
  - one process (`tikray serve`, holding `state/serve.lock`) owns the state, and now `auth.json` too;
  - the API is HTTPS with the pinned self-signed certificate;
  - the default policy sends everything direct;
  - kill-switch traffic never goes direct;
  - errors carry their package prefix;
  - stdlib first.
- **Secrets never appear** in logs, events, errors, history or API responses. They are:
  - M2b's: server credentials, subscription URLs, the root token;
  - passwords and password hashes;
  - the setup code;
  - session ids;
  - CSRF tokens (except the response that hands one to its own session);
  - API tokens and their hashes (except the one response that creates a token);
  - the CSRF key.

  The setup code is shown only by `tikray setup-code` and in the `setup.code` file.
- **Files:**
  - `auth.json` and `setup.code` are 0600 in the 0700 state directory, written with `internal/atomicfile`;
  - `run/hot/` is 0700, and its files are 0600 and removed after use.
- **Fixed values:**
  - **argon2id:** m = 19456 KiB, t = 2, p = 1, a 16-byte salt and a 32-byte key, stored as a PHC string (`$argon2id$v=19$m=19456,t=2,p=1$<salt b64>$<hash b64>`). At most 2 hashes run at once (each holds 19 MiB); more wait, bounded by their context.
  - **Passwords:** 10 to 256 bytes, and not equal to the username.
  - **Usernames:** 1 to 64 runes, and no rune `store.ForbiddenInName` refuses.
  - **Setup code:** 12 symbols of Crockford base32 (`0123456789ABCDEFGHJKMNPQRSTVWXYZ`), shown as `XXXX-XXXX-XXXX`. Input is normalised: upper-cased, `-` and spaces dropped, `O`→`0`, `I` and `L`→`1`.
  - **Sessions:**
    - The id is 32 random bytes, base64url. Only its SHA-256 is stored.
    - The idle limit is 12 h and the absolute limit is 7 days.
    - At most 20 sessions are kept; the oldest goes first.
    - The cookie is `tikray_session` with `Secure; HttpOnly; SameSite=Strict; Path=/`.
  - **CSRF:**
    - Header `X-Tikray-CSRF`.
    - The token is `base64url(HMAC-SHA256(csrf_key, session id))`, so nothing more is stored.
    - It is required on every cookie-authenticated request whose method isn't GET or HEAD.
    - Bearer requests are exempt.
  - **API tokens:**
    - The format is `tkr_<8 hex id>_<43 base64url chars>` (32 random bytes). Only the SHA-256 of the secret part is stored.
    - Names are 1 to 64 runes, and at most 50 tokens are kept.
    - A token may have an expiry.
    - `last_used` is kept in memory and saved at most every 10 min.
  - **Rate limit:** setup and sign-in failures only.
    - Per client IP: a bucket of 5 that refills 1 per 60 s.
    - Global: a bucket of 100 that refills 1 per 9 s.
    - An empty bucket answers 429 with `Retry-After` before any hashing.
- **The root token** (`api.token`) keeps every M2b right, and is the only credential that may reset the admin (`POST /v1/auth/reset`).
- **Hot changes** apply only when the candidate render differs from the active config in nothing but `outbounds` entries whose tag starts with `srv-` (added, removed or changed, compared as canonical JSON). The core and geo must be the same, and the runner must be `running`. `TIKRAY_HOT=off` makes every apply a trial.
- **Commits:** the repo's git identity is `Arman2122 <arman.seyri@gmail.com>`; messages carry no trailers; never push.

## Review Focus

1. **Guessing a password or the setup code.**
   - A wrong username and a wrong password give the same answer, in the same time. A dummy hash runs for an unknown user.
   - After 5 failures from an IP the 6th attempt is 429 with no hash computed.
   - A flood can't run more than 2 argon2 hashes at once.
   (Task 2 `TestSignInSameAnswerAndTime`, `TestRateLimitBeforeHashing`, `TestHashConcurrencyBounded`.)
2. **CSRF.**
   - A cookie-authenticated PUT, POST or DELETE without the header, or with another session's token, is 403 and changes nothing.
   - A bearer request needs no header.
   - No GET changes the state.
   (Task 3 `TestCSRFRequiredForCookies`, `TestBearerNeedsNoCSRF`.)
3. **Session lifecycle.**
   - Signing out, changing the password (which ends every other session), the idle and absolute limits, and the 20-session cap all hold.
   - A daemon restart keeps sessions and tokens.
   - A revoked token gets 401 at once.
   (Task 2 `TestSessionLimits`, Task 3 `TestPasswordChangeEndsOtherSessions`, e2e `restart_keeps_auth`.)
4. **A hot change that half-fails.**
   - An `rmo` succeeds and then the `ado` fails, or the proxy probe fails after the change: the apply falls back to a full trial with the same candidate, which restarts xray from it, so the partial hot state is gone.
   - If tikray dies between the hot calls and the adopt, the next pass sees the active config differ from the render and heals (the hot attempt fails on the existing tag, then a trial).
   (Task 6 `TestHotFallsBackToTrial`, `TestHotInterruptedHeals`.)
5. **Hot changes only where they're safe.**
   - A change to rules, DNS, a device, a pin or the balancer membership (zero servers to some, which changes rules and observatory) always goes through a trial.
   - Hot changes never run during a trial or a core update.
   - The adopted config survives a runner restart.
   (Task 6 `TestHotOnlyForServerOutbounds`, Task 5 `TestAdoptOnlyWhileRunning`, e2e `hot_survives_runner_restart`.)

- Produces:
  - `NewHandler(b Backend, root string, a *auth.Store, lim *auth.Limiter, …)` (keep M2b's options).
  - **Authentication, in order:**
    1. `Authorization: Bearer <root>` (constant time);
    2. `Authorization: Bearer tkr_…` through `CheckToken`;
    3. the `tikray_session` cookie through `Session`.

    Otherwise 401. The client IP is the request's remote address; M3's firewall decides who can reach the port.
  - **CSRF:** a cookie-authenticated request whose method isn't GET or HEAD needs `X-Tikray-CSRF` to pass `CheckCSRF`, or it is 403 `csrf`. Bearer requests skip it.
  - **Public routes:**
    - `GET /healthz`;
    - `GET /v1/auth/state` → `{"setup_required", "signed_in"}`;
    - `POST /v1/auth/setup {code, username, password}`;
    - `POST /v1/auth/login {username, password}`.

    Setup and login go through the limiter. A failure is 401 `bad_credentials` (or `bad_code`); an empty bucket is 429 `rate_limited` with `Retry-After`. A success sets the cookie and returns `{"csrf_token", "expires"}`.
  - **Session routes:**
    - `GET /v1/auth/session` → `{"username", "csrf_token", "expires"}` (cookie only);
    - `POST /v1/auth/logout`;
    - `PUT /v1/auth/password {current, new}` (cookie: keeps this session, ends the others).
  - **Token routes** (any authenticated caller):
    - `GET /v1/tokens`;
    - `POST /v1/tokens {name, expires_in}` → 201 with `{token, info}`, the only time the secret is sent;
    - `DELETE /v1/tokens/{id}`.
  - **Root only:** `POST /v1/auth/reset` (a session or a named token gets 403).
  - **Headers on every response:** `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY`, `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`, and M2b's `Cache-Control: no-store`.
  - **Events:** a new service kind `auth` (add the constant beside M2b's) records:
    - setup completed;
    - signed in and sign-in failed (with the username, cut to 64 runes, and the client IP; never the password);
    - signed out;
    - password changed;
    - token created and revoked (name and id);
    - admin reset.

    The handler reaches the event recorder through `Backend` (add `Record(kind, msg string)`).

### Task 6: Artifacts: hot changes, with the trial as the fallback

**Files:**
- Create: `internal/artifacts/hot.go`.
- Modify: `internal/artifacts/core.go` (Apply, Result), `cmd/tikray/main.go` (`newUpdater`: the `Hot` field and `TIKRAY_HOT`).
- Test: `internal/artifacts/hot_test.go`, `internal/artifacts/apply_test.go`.

**Interfaces:**
- Consumes: Task 5 `Client.Adopt`; M1's `Client.XrayAPI`; M2b's `Client.Test`, `ProxyHealth` and baseline.
- Produces:
  - `CoreUpdater.Hot bool`: when true, `Apply` tries the hot path first. `cmd/tikray` sets it true unless `TIKRAY_HOT=off`. Core updates and rollbacks never use it.
  - `CoreUpdater.XrayAPIServer string`: the `--server=` address for `xray api`, the same as `XrayAPIProbe`'s (`cfg.XrayAPI`).
  - `CoreUpdater.RunnerRun string`: the runner's own path of `run/`, which `xray api ado` reads the file from. It defaults to `/data/run`, the runner image's mount; tests set it to their temp dir.
  - `Result.Hot bool` (JSON `hot,omitempty`).
  - `func hotPlan(active, candidate []byte) (plan, bool)`. It parses both configs, compares every top-level key except `outbounds` as canonical JSON, and diffs the outbounds by tag. The plan qualifies only if:
    - every difference is in an outbound whose tag starts with `srv-`;
    - the outbounds' order outside `srv-` is unchanged;
    - the non-`srv-` outbounds are identical.

    `plan{remove []string; add []json.RawMessage}`, where a changed tag is in both.
- **The hot path in `Apply`:** under the artifacts lock, after the noop check and with `NoState` handled as now.
  1. **Candidate:** read the active config from `run/<active.Config>` and render the candidate. Qualify the plan, and require runner state `running`.
  2. **Test:** write the candidate content-addressed (as the trial does) and `Runner.Test` its bytes. If it is rejected, the outcome is `rejected`, as a trial's `-test` would give, and nothing has been touched.
  3. **Baseline:** run `ProxyHealth` once (M2b's baseline).
  4. **Remove:** for each tag in `remove`, call `XrayAPI` with `rmo --server=<addr> <tag>`. A non-zero exit is a hot failure.
  5. **Add:** write `{"outbounds":[…add…]}` to `run/hot/<sha256>.json` (0600 in 0700) and call `XrayAPI` with `ado --server=<addr> <RunnerRun>/hot/<sha256>.json`. Remove the file afterwards.
  6. **Probe again:** if the baseline passed, `ProxyHealth` must pass within `HealthWindow`.
  7. **Adopt:** `Runner.Adopt(candidate config)`.
  8. **Result:** `Outcome: committed`, `Hot: true`, Detail `applied without restarting xray: added A, removed R, changed C`. History is recorded and pruning runs as for a committed trial.
  - **Fallback:** a failure in steps 4–7 runs the full trial with the same candidate. Its Detail starts `the hot change failed (<redacted reason>), so it was applied with a trial: `. A plan that doesn't qualify, or a runner that isn't `running`, goes straight to the trial with no note.
