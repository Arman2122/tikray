# M2b: the tikray service Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `tikray serve` keeps xray in step with the desired state.
- It owns the state, applies every change through the runner's trial, refreshes subscriptions on schedule and watches server health.
- It exposes all of this through an HTTPS API with a bearer token. The `tikray` CLI uses that API.
- The whole flow is tested end to end on RouterOS CHR.

**Architecture:** M2 now comes in three parts.
- **M2a** (merged): the model and the config.
- **M2b** (this plan): the long-running service.
  - `internal/xray`: a minimal gRPC client for xray's stats, observatory and routing services.
  - `internal/health`: the monitor.
  - `internal/service`: owns the store, the apply loop, the mutations and the subscription scheduler.
  - `internal/api` and `internal/apiclient`: the HTTPS API and its client.
  - `tikray serve` and the CLI commands over the API.
  - A runner endpoint that tests one config.
  - It also lands the M2a carries that the service builds on.
- **M2c** (next plan): human sign-in on the same listener: the setup code, argon2id, sessions, CSRF, rate limiting and API tokens (§7). Hot changes through `xray api` (§3.4) move to M2c or later.

**Tech Stack:** Go 1.24 (module `github.com/Arman2122/tikray`), the stdlib, `golang.org/x/net/http2` (already a dependency through `x/net`) for gRPC over h2c, and `google.golang.org/protobuf/encoding/protowire` (already in the module graph) for the wire messages. **No `google.golang.org/grpc` and no generated code.** The lab is M0–M2a's `test/lab` and `test/e2e`.

**Spec:** `docs/superpowers/specs/2026-10-24-tikray-design.md`: §3.4, §3.6, §4.2, §4.5, §5.6, §6.3 (the `/healthz` the watchdog will poll), §7, §8.1, §8.4 and §10.

M2a's carries and rulings are in the M2a plan's "(changed: …)" notes and in the M2a PR (Arman2122/tikray#4). This plan names each carry where it is built.

## Global Constraints

- Everything in M2a's Global Constraints still holds:
  - the tags, ports and bridge addresses (router `.1`, tikray `.2`, runner `.3`);
  - no image contains xray or geo data;
  - kill-switch traffic never goes direct;
  - errors carry their package prefix;
  - stdlib first.
- **One process owns the state:** the `tikray serve` daemon.
  - While it runs, every state change goes through its API. The CLI never writes `state.v<N>.json` itself when the daemon is reachable.
  - Without the daemon, only M2a's direct paths remain: `core update [--config]`, `core rollback`, `apply`, `config render`, `core list|status`.
- **The API:**
  - HTTPS on `TIKRAY_LISTEN`, default `:443`. In the container the only interface is the bridge veth, so this means tikray's bridge address.
  - The certificate is self-signed ECDSA P-256, created on first start: `<data>/state/tls.crt` (0644) and `tls.key` (0600). It is reused on every later start.
  - The token is `<data>/state/api.token` (0600): 32 random bytes as lowercase hex, created on first start and reused. Every request needs `Authorization: Bearer <token>`, compared in constant time; the one exception is `GET /healthz`.
- **Secrets never appear** in API error bodies, events, logs, `Result.Detail` or the history. Secrets are:
  - server credentials (any string value under an outbound's `id`, `password`, `privateKey`, `preSharedKey` or `seed`);
  - subscription URLs;
  - the API token.

  xray's own output is redacted before it is recorded (carry from M2a).
- **The default policy is unchanged:** a fresh install sends everything direct until the user adds servers and devices.
- **Commits:** the repo's git identity is `Arman2122 <arman.seyri@gmail.com>`; messages carry no trailers; never push.

## Review Focus

1. **State changes that land during an apply or a core update.** The applied config must end up reflecting the newest state, never an older one. An edit made while an apply runs leads to another apply after it (Task 7 `TestApplyCatchesUpWithLaterEdits`).
2. **The runner unreachable or restarting during an apply or a refresh.**
   - No state is lost; the apply retries with backoff, and status says it is pending, not applied.
   - A refresh that can't reach the runner for its per-server test still merges, with the servers marked untested, and the trial is the net.
   - (Task 7 `TestApplyRetriesWhenRunnerDown`, Task 9 `TestRefreshWithoutRunner`.)
3. **A refresh that removes the pinned server, or one a custom rule names.** The new state stays valid: the pin is cleared, rules that name a removed server are dropped, and both are recorded as events. The refresh never leaves a half-done or failed update (Task 9 `TestRefreshClearsReferences`).
4. **Secrets in API responses, events and logs:**
   - a refused server's xray output that repeats its id;
   - a subscription URL in a fetch error;
   - the token in a log line.
   (Task 4 `TestRedactDetail`, Task 9 `TestRefreshErrorsHaveNoURL`, Task 10 `TestErrorsHaveNoSecrets`.)
5. **A daemon restart.** The state and the applied config persist. A daemon that starts in sync runs no trial. The token and the certificate are reused, never regenerated (Task 7 `TestStartInSyncAppliesNothing`, Task 10 `TestTokenAndCertReused`, e2e `restart_persists`).

### Task 5: A minimal gRPC client for xray

**Interfaces:**
- Produces:
  - `type Client struct{ Addr string; Timeout time.Duration }`. `Addr` is host:port; a zero `Timeout` means 5 s.
  - `func (c *Client) QueryStats(ctx context.Context, pattern string, reset bool) ([]Stat, error)` with `type Stat struct{ Name string; Value int64 }`.
  - `func (c *Client) SysStats(ctx context.Context) (SysStats, error)` with `type SysStats struct{ Uptime uint32; NumGoroutine uint32; Alloc uint64 }`.
  - `func (c *Client) OutboundStatus(ctx context.Context) ([]OutboundStatus, error)` with `type OutboundStatus struct{ Tag string; Alive bool; Delay time.Duration; LastError string; LastSeen, LastTry time.Time }`. Delay is milliseconds on the wire.

  - `type StatusError struct{ Code int; Message string }` for a non-zero `grpc-status`.

  - A unary call is an HTTP/2 POST over h2c (`http2.Transport{AllowHTTP: true, DialTLSContext: <plain TCP dial>}`) to `/<service>/<method>`.
  - Headers: `content-type: application/grpc`, `te: trailers`.

  - The services are `xray.app.stats.command.StatsService` (`QueryStats`, `GetSysStats`), `xray.app.observatory.command.ObservatoryService` (`GetOutboundStatus`) and `xray.app.router.command.RoutingService` (`GetBalancerInfo`).     - `app/stats/command/command.proto`;

- **The checks, in order.** Servers are M2a's `lab-a` and `lab-b` share links. The device is the lab LAN client.
  1. `serve_starts`: the tikray container runs its default `serve`. Within 60 s, `/healthz` answers with the pinned certificate, the token works, and `status` shows revision 0 and level `down` or `idle`. (changed: the test unsets the container's `cmd` (`/container/unset [find name=tikray] cmd`) before it starts it. RouterOS keeps the image's CMD as `default-cmd` and runs it only while `cmd` is unset: with `cmd=""`, the first run's way, the entrypoint ran without `serve` and tikray exited 2 with its usage. The check also compares the PEM's fingerprint with the one `serve` printed in the container log, and runs `tikray status` at `/container/shell … cmd=`, whose output must hold the status's `revision` line, so that `sh: tikray: not found` fails it.)
  2. `bootstrap_core`: `POST /v1/core/update {"version":"latest"}` commits a default render; the LAN client goes direct (whoami `198.51.100.2`).
  3. `add_server_applies`: `POST /v1/servers` with `lab-a`'s link, then `PUT /v1/devices/…` smart. Within 60 s, `status.applied` is true, whoami goes through server a, and `GET /v1/health` shows `lab-a` alive and selected. (changed: liveness and the pick are read from `GET /v1/status`'s `health` (`servers[]`, `selected`), P9; and first `PUT /v1/health` sets the lab's probe URL, `http://203.0.113.30/whoami`, which the observatory probes, as in every M2a lab state.)
  4. `subscription_refresh`: `setSub("lab", base64(lab-b link))`, then `POST /v1/subscriptions` for `http://203.0.113.30/sub/lab` and `POST …/refresh` → `added: 1`. After the apply, stop server a: whoami goes through b within 30 s. (changed: the check stops the server the status names as `selected`, once whoami goes through it too, and wants whoami through the other within 30 s, and lab-b, the subscription's server, to have carried the traffic before the stop or after it: the balancer often picked lab-b, which left "stop a" with nothing to switch. A new subscription is due at the scheduler's next look, so a manual refresh that finds lab-b `kept: 1` passes only when a refresh event of that subscription says `added 1`; the results say which it was. Task 13's fix round.)
  5. `subscription_block_page`: `setSub("lab", "<html>blocked</html>")`, then refresh → 422 or a failure result. `last_error` is set and `lab-b` is still present. (changed: the refresh is 502 `fetch_failed`, P7, and its detail must say that both `direct:` and `proxy:` got the page and refused it; neither the error nor `last_error` names the subscription's URL. A fetch falls back to the proxy only while `ProxyHealthy` holds, so the check first waits for the status to show the runner `running` with its gateway up, the server that is up alive and the stopped one dead. The first committed runs had `direct:` alone, since the monitor's snapshot still showed the refresh's apply in `trial`, which led to `Monitor.Poke`; Task 13's fix round.)
  6. `outage_apply`: stop both servers, then `PUT` the device with the kill switch → within 90 s, `status.applied` is true (the baseline skipped the proxy probe) and whoami fails for 30 s. Start a: proxied within 30 s.
  7. `refused_server`: `POST /v1/servers` with a raw VLESS outbound whose id is 40 non-UUID characters, to `203.0.113.10` → 422 `refused`. The detail lacks the id, and the revision is unchanged.
  8. `restart_persists`: `/container/stop` then `/container/start` tikray → `status` shows the same revision, `applied: true`, no new `apply` event (no trial), and the same certificate fingerprint and token. (changed: events live in memory, so "no new" is none in the restarted service's list 20 s after the start. The status must also have nothing `pending`, and the runner, 20 s after the start, must be `running` with no candidate, its active selection and last trial as before; Task 13's fix round.)
