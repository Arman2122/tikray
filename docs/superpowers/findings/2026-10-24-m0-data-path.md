# M0 findings: the data path on RouterOS

- **Date:** 2026-10-24
- **Plan:** `docs/superpowers/plans/2026-10-24-m0-data-path-spike.md`
- **Spec:** `docs/superpowers/specs/2026-10-24-tikray-design.md`
- **Raw results:** `spike/m0/results/*.json`

## Verdict

**The design holds.** On real RouterOS 7.25 and 7.23.8 (CHR), traffic goes from a LAN device through RouterOS policy routing into a container, through xray's TUN inbound and out over VLESS. The xray-core versions tested are the lab's 26.3.27 and the newest release, 26.10.21. Every assumption in §10 M0 was confirmed, with four corrections to the design:

1. **Routing marks must apply only to the original direction** (spec §5.2). Otherwise fail-open fallback never works.
2. **xray's domestic DNS server needs `skipFallback: true`** (spec §5.4). Otherwise every lookup can go to the domestic resolver, which defeats proxied DNS.
3. **RouterOS can't run the image archives written by Docker's default (containerd) image store, and a container won't start without explicit DNS** (spec §6.1, §8.6).
4. **Files placed on the router by RouterOS have no execute bit** (spec §3.3). The runner has to stage the core binary before running it.

The TPROXY fallback from spec §11 isn't needed. The TUN inbound works in a RouterOS container without `privileged` or `devices`.

## What was tested

The lab is the `test/lab` harness (kept for M3):
- RouterOS CHR in QEMU (TCG emulation, no KVM) sits between a fake LAN (netns `tklab-client`) and a fake internet (netns `tklab-inet`).

## Findings

### Data path

- **TUN inbound in a RouterOS container works** with `privileged=no` and no `devices`. xray creates `xray0`. The runner sets forwarding and `rp_filter=0` through `/proc/sys` and adds `iif <ingress> lookup 1001` and `default dev xray0 table 1001` via netlink.
- **The container's interface is named after the veth** (for example `tikray-runner`), not `eth0`. Finding the ingress link from the default route works.
- **Sniffing with `routeOnly` splits by domain on the same IP**, and xray's access log shows the device's own source address (no source NAT).
- **The minimum xray version for the TUN inbound is 26.1.18.** Module v1.260118.0 is the first containing `proxy/tun`; 25.12.8 doesn't have it.
- **xray 26.10.x blocks private and reserved targets on server inbounds.** Its `freedom` outbound, when reached through a server inbound (VLESS, VMess, Trojan, Hysteria, WireGuard, Shadowsocks), blocks private and reserved destination IPs by default ("blocked target … blackholing connection").
  - This broke the lab's test VLESS server, because the fake internet is TEST-NET-3. The fixture now allows that range with `finalRules`.
  - tikray's client side isn't affected: traffic from TUN, socks and dokodemo inbounds isn't covered.
  - It's the kind of upstream default change the CI compatibility matrix (spec §8.2) must catch on every new release.
- **xray 26.10.21 renamed the TUN `MTU` key to `mtu`.** Existing configs keep working because the config is parsed case-insensitively. It also adds Linux options (`gateway`, `dns`, `autoSystemRoutingTable`, `autoOutboundsInterface`, `autoSystemDnsToGateway`) that could replace part of the runner's netlink setup. Keeping the runner-managed routes keeps every version from 26.1.18 working.

### Design corrections

1. **Fail-open fallback needs direction-aware routing marks** (`fallback_open` failed in the first run).
   - `check-gateway=ping` notices a stopped runner within about 20–30 s, and the WAN fallback route becomes active.
   - But new connections still timed out. Replies of masqueraded connections reach mangle prerouting before the NAT is undone, so their destination is the WAN address, which isn't in `tikray-local`. A `mark-routing` rule matching only `connection-mark=tikray-open` therefore routed the SYN-ACKs back out the WAN.
   - Adding the source list to the `mark-routing` rules (original direction only) fixed it. After that, fallback took about 25 s and recovery about 12 s after the runner reported ready.
2. **DNS: the domestic resolver must not be a fallback** (`dns_proxied` failed in the first run).
   - In xray, a DNS server with `domains` still serves as a fallback for every other domain unless it has `skipFallback: true`. `foreign.test` went to the domestic resolver, direct.
   - The access log names these internal queries `from DNS … [xray.system.<uuid> -> …]`, routed by the normal rules.
3. **The FastTrack exemption must be created in one script block** (`no_fasttrack_marked` failed in the first run).
   - In `/import`, a `:local` set on one top-level line is gone on the next, so the accept rules were silently never created.
   - Even without them, RouterOS 7.25 flagged routing-marked connections `F` but fast-pathed zero of their packets, so traffic stayed correct. The accept rule still keeps them unflagged.

### Containers on RouterOS

- **Image format:** RouterOS rejects archives from Docker 29's default containerd image store ("no config found in manifest"). It accepts `docker save` output from the classic store (`"features": {"containerd-snapshotter": false}`). The tikray release pipeline must produce archives RouterOS accepts and test the import in CI.
- **DNS is required:** a container won't start with "no default dns servers, explicitly set empty dns override if intended" until the container itself has `dns=`. Setting `/ip/dns` servers isn't enough.
- **Mounts:**
  - `/container/mounts/add` takes `list=` (not `name=`), `src`, `dst` and `mode` (`ro`, `ro,noexec`, `rw`, `rw,noexec`). Containers use `mountlists=`.
  - Read-only mounts are enforced: the runner's write to its `ro` cores mount fails.
  - Files written by one container are visible to the other.
- **Envs:** `/container/envs/add list= key= value=`, and containers use `envlists=`.
- **More container options:** `/container/add` also has `memory-high`/`memory-max`, `restart-policy`, `healthcheck-*`, `devices` and `privileged`. These are useful for spec §3.3 and §6.3, since RouterOS can restart a failed container itself.
- **No execute bit:** files placed by `/tool/fetch` (and Winbox uploads) have no execute bit, and RouterOS has no `chmod`. Running xray from the mount fails with "permission denied". The runner prototype copies the core to its own filesystem with mode 0755 and runs it from there.
- **Reboots:** after a power cycle, containers with `start-on-boot=yes` come back and the runner re-applies its routes within seconds of SSH being up.

### RouterOS integration

- **API-SSL with a restricted user works:**
  - The `tikray` group has `policy=read,write,api` and the user is limited to `address=172.31.255.2/32`.
  - `/ip/firewall/address-list/listen` delivers change events to the control container.
  - SSH as `tikray` is refused.
- **The self-signed API certificate must keep `key-cert-sign`.** `/certificate/sign` fails with "CA not found" if `key-usage` is narrowed to `tls-server`.
- **RouterOS throttles bursts of SSH logins.** A correct login right after a failed one, or a quick burst of new connections, is rejected. Clients should keep one connection open (the lab harness now does). The control plane's API client should do the same and back off on refused logins.

### Lab and CI facts (for M3)

- **CHR boot times under TCG emulation:** about 2–4 min to the login prompt on x86_64, and a soft reboot takes 4–6 min until SSH answers.
- **Device-mode on CHR is confirmed by a cold power cycle** (killing QEMU).
- **The data disk appears as slot `pcie1`.** `/disk/format-drive` doesn't exist on 7.25; `/disk/format` does. Renaming the slot to `disk1` keeps paths stable.
- **CHR's free license caps each interface at about 1 Mbps** (122,845 B/s measured). Lab timings are not throughput data; throughput needs the hardware kit (`spike/m0/hw`).
- **The first-boot prompts** (license, forced password change) were the same on 7.23.8 and 7.25.

## Hardware
