# M0 findings: the data path on RouterOS

- **Date:** 2026-10-24
- **Plan:** `docs/superpowers/plans/2026-10-24-m0-data-path-spike.md`
- **Spec:** `docs/superpowers/specs/2026-10-24-tikray-design.md`
- **Raw results:** `spike/m0/results/*.json`

## Verdict

**The design holds on x86_64 CHR.** On RouterOS 7.25 and 7.23.8 (CHR x86_64), traffic goes from a LAN device through RouterOS policy routing into a container, through xray's TUN inbound and out over VLESS. The xray-core versions tested are the newest release, 26.10.21, and 26.3.27. The full run on ARM64 CHR, the product target, is still running; until it passes, these results are x86_64 only. Throughput and CPU on real hardware are still open (see Hardware).

The data-path assumptions in spec §10 (M0) held, with six corrections to the design:

1. **Packets addressed to the router must never get a routing mark, and routing follows the connection mark alone** (spec §5.2). Otherwise fail-open fallback never works, or a device that changes policy loses its open connections.
2. **xray's domestic DNS server needs `skipFallback: true`** (spec §5.4). Otherwise every lookup can go to the domestic resolver, which defeats proxied DNS.
3. **DNS has to fall back with the routes** (spec §5.4). A fail-open device whose DNS stays dst-NATed to a dead runner is offline even though its traffic could go direct.
4. **The runner must stop answering ping when xray is down** (spec §3.3). `check-gateway` only sees the container, so a dead xray inside a live runner would otherwise black-hole fail-open traffic.
5. **RouterOS can't run the image archives written by Docker's default (containerd) image store, and a container won't start without explicit DNS** (spec §6.1, §8.6).
6. **Files placed on the router by RouterOS have no execute bit** (spec §3.3). The runner has to stage the core binary before running it.

Corrections 3 and 4 and the second half of 1 came from the whole-branch review, not from the first test list; the checks `fallback_open` (its DNS part), `xray_dead_fallback` and `policy_switch_existing_conn` were added for them.

The TPROXY fallback from spec §11 isn't needed. The TUN inbound works in a RouterOS container without `privileged` or `devices`.

## Findings

### Data path

- **TUN inbound in a RouterOS container works** with `privileged=no` and no `devices`. xray creates `xray0`. The runner sets forwarding and `rp_filter=0` through `/proc/sys` and adds `iif <ingress> lookup 1001` and `default dev xray0 table 1001` via netlink.
- **The container's interface is named after the veth** (for example `tikray-runner`), not `eth0`. Finding the ingress link from the default route works.
- **Sniffing with `routeOnly` splits by domain on the same IP**, and xray's access log shows the device's own source address (no source NAT).
- **The minimum xray version for the TUN inbound is 26.1.18.** Module v1.260118.0 is the first containing `proxy/tun`; 25.12.8 doesn't have it.
- **xray 26.10.x blocks private and reserved targets on server inbounds.** Its `freedom` outbound, when reached through a server inbound (VLESS, VMess, Trojan, Hysteria, WireGuard, Shadowsocks), blocks private and reserved destination IPs by default ("blocked target … blackholing connection").
  - This broke the lab's test VLESS server, because the fake internet is TEST-NET-3. The fixture now allows that range with `finalRules`.
  - tikray's client side isn't affected: traffic from TUN, socks and dokodemo inbounds isn't covered.
  - It's the kind of upstream default change the CI compatibility matrix (spec §8.2) must catch on every new release.
- **xray 26.10.21 renamed the TUN `MTU` key to `mtu`.** Existing configs keep working because the config is parsed case-insensitively. It also adds Linux options (`gateway`, `dns`, `autoSystemRoutingTable`, `autoOutboundsInterface`, `autoSystemDnsToGateway`) that could replace part of the runner's netlink setup. The runner keeps managing the routes itself, so it doesn't depend on options only newer versions have. M0 ran 26.3.27 and 26.10.21; 26.1.18 itself wasn't run.

### Design corrections

1. **Packets addressed to the router must not be marked** (`fallback_open` failed in the first run).
   - `check-gateway=ping` notices a stopped runner within about 20–30 s, and the WAN fallback route becomes active.
   - But new connections still timed out. Replies of masqueraded connections reach mangle prerouting before the NAT is undone, so their destination is the WAN address, which isn't in `tikray-local`. A `mark-routing` rule matching only `connection-mark=tikray-open` therefore routed the SYN-ACKs back out the WAN.
   - The first fix also matched the source list in `mark-routing`, so only the original direction was marked. The review found that this breaks a device that changes policy: its open connections lose their routing mark and leave through the WAN without NAT.
   - The rule set now starts with `dst-address-type=local action=return`, and `mark-routing` matches the connection mark alone. A connection keeps one path for its whole life; the reconciler removes a device's tracked connections when its policy changes (spec §5.2).
2. **DNS: the domestic resolver must not be a fallback** (`dns_proxied` failed in the first run).
   - In xray, a DNS server with `domains` still serves as a fallback for every other domain unless it has `skipFallback: true`. `foreign.test` went to the domestic resolver, direct.
   - The access log names these internal queries `from DNS … [xray.system.<uuid> -> …]`, routed by the normal rules.
3. **The FastTrack exemption must be created in one script block** (`no_fasttrack_marked` failed in the first run).
   - In `/import`, a `:local` set on one top-level line is gone on the next, so the accept rules were silently never created.
   - In that one 7.25 run without the rules, routing-marked connections were flagged `F`, but none of their packets were fast-pathed, so traffic stayed correct. One run isn't a guarantee, so the accept rule stays.
4. **DNS has to fall back too** (found in review; `fallback_open` now checks DNS).
   - The DNS dst-NAT rules for fail-open devices kept pointing at the stopped runner, so lookups timed out while the routes had already fallen back.
   - A RouterOS netwatch on the runner now disables the fail-open DNS rules while the runner doesn't answer ping and enables them again when it does. Kill-switch devices keep pointing at the runner. The router's DNS has to accept LAN requests (`allow-remote-requests=yes`).
5. **xray dead inside a live runner** (found in review; `xray_dead_fallback`).
   - `check-gateway` pings the runner's address, which the container answers whether or not xray runs. With xray stopped, fail-open traffic was sent to the runner and dropped there.
   - The runner now sets `icmp_echo_ignore_all` while xray isn't running or its routes are missing, so `check-gateway` and the netwatch see the outage. Table 1001 also gets a low-priority `unreachable` default, so packets that arrive in the gap are rejected instead of bounced back to the router.

### Containers on RouterOS

- **Image format:** RouterOS rejects archives from Docker 29's default containerd image store ("no config found in manifest"). It accepts `docker save` output from the classic store (`"features": {"containerd-snapshotter": false}`). The tikray release pipeline must produce archives RouterOS accepts and test the import in CI.
- **DNS is required:** a container won't start with "no default dns servers, explicitly set empty dns override if intended" until the container itself has `dns=`. Setting `/ip/dns` servers isn't enough.
- **Mounts:**
  - `/container/mounts/add` takes `list=` (not `name=`), `src`, `dst` and `mode` (`ro`, `ro,noexec`, `rw`, `rw,noexec`). Containers use `mountlists=`.
  - Read-only mounts are enforced: the runner's write to its `ro` cores mount fails.
  - Files written by one container are visible to the other.
- **Envs:** `/container/envs/add list= key= value=`, and containers use `envlists=`.
- **More container options:** `/container/add` also has `memory-high`/`memory-max`, `restart-policy`, `healthcheck-*`, `devices` and `privileged`. These are useful for spec §3.3 and §6.3, since RouterOS can restart a failed container itself.
- **No execute bit:** files placed by `/tool/fetch` (and Winbox uploads) have no execute bit, and RouterOS has no `chmod`. Running xray from the mount fails with "permission denied". The runner prototype copies the core to its own filesystem with mode 0755 and runs it from there.
- **Reboots:** after a power cycle, containers with `start-on-boot=yes` come back and the runner re-applies its routes within seconds of SSH being up.

### RouterOS integration

- **API-SSL with a restricted user works:**
  - The `tikray` group has `policy=read,write,api` and the user is limited to `address=172.31.255.2/32`.
  - `/ip/firewall/address-list/listen` delivers change events to the control container.
  - SSH as `tikray` is refused.
- **The self-signed API certificate must keep `key-cert-sign`.** `/certificate/sign` fails with "CA not found" if `key-usage` is narrowed to `tls-server`.
- **Netwatch waits 5 minutes after boot by default** (`startup-delay=5m`). The runner watch sets `startup-delay=0s`, or fail-open DNS stays pointed at a dead runner for the first minutes after every boot. The fix-pass run caught this because its checks start within 5 minutes of boot.
- **RouterOS throttles bursts of SSH logins.** A correct login right after a failed one, or a quick burst of new connections, is rejected. Clients should keep one connection open (the lab harness now does). The control plane's API client should do the same and back off on refused logins.

### Lab and CI facts (for M3)

- **CHR boot times under TCG emulation:** about 2–4 min to the login prompt on x86_64, and a soft reboot takes 4–6 min until SSH answers.
- **Device-mode on CHR is confirmed by a cold power cycle** (killing QEMU).
- **ARM64 CHR needs `-cpu cortex-a72`.** On QEMU 8.2's `-cpu max` its kernel hangs right after the EFI stub (the guest idles, nothing on the console), with or without ACPI. On `cortex-a72` it reaches the login prompt in about 90 s.
- **The data disk appears as slot `pcie1`.** `/disk/format-drive` doesn't exist on 7.25; `/disk/format` does. Renaming the slot to `disk1` keeps paths stable.
- **CHR's free license caps each interface at about 1 Mbps** (122,845 B/s measured). Lab timings are not throughput data; throughput needs the hardware kit (`spike/m0/hw`).
- **The first-boot prompts** (license, forced password change) were the same on 7.23.8 and 7.25.

## Hardware

Real-hardware throughput, CPU and memory are **pending**. Run the kit in `spike/m0/hw/` (README there) on a hAP ax³ or RB5009 and add the filled-in `results-template.md` here. The lab can't measure throughput: CHR's free license caps each interface at about 1 Mbps.

In the lab, xray 26.10.21 used about 29 MB RSS (`xray_rss_kb=29816`). RouterOS reported 70 MiB `memory-current` for the runner container, which includes the staged core binary in page cache, and under 2 MiB for the control container.

## Coverage gaps carried forward

- **ARM64:** the full run on ARM64 CHR (stable) was still running when this was written. The product target is ARM64, so M0 isn't done until it passes.
- **MTU boundaries:** every lab hop has a 1500-byte MTU, so `large_transfer` shows that transfers arrive intact, not that the MSS clamp or a smaller WAN MTU (PPPoE, 1492) works. That moves to the hardware kit and the M3 suite.
- **QUIC sniffing** isn't exercised (no QUIC fixture); plain UDP is. It moves to the M3 end-to-end suite.
- **Throughput and CPU on real ARM64 hardware** are pending the hardware kit (`spike/m0/hw/README.md`).
- **IPv6 leak guard:** out of M0's scope; covered in M3.
