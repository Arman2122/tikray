## Residual finding (Important) — fixed in 25d9446 at your request

The runner cached `xray version` per core name for its whole life (`internal/runner/runner.go:479-489`). The pre-commit version check reads that cache, so after a core was pruned and reinstalled under the same name, an update could be refused although the new binary was correct, or passed although it was mislabeled, until the runner container restarted.

Fix (25d9446): `versionOf` keys the cached text by the slot binary's size and mtime, the same identity the supervisor uses to decide whether to restage, and asks xray again when either differs. Test `TestVersionFollowsReinstalledCore` fails on 9442e31 ("fake ok" where "fake exit15s" was wanted) and passes with the fix. A scoped re-review found it addressed on every path that reports a version (boot, trial, restart, reload, backoff restart, revert), with no new breakage.

Two nits from that review are deferred: an unstat-able slot now reports "" even when a cached text existed (fails closed), and runner.go:496 spells out `r.cfg.Supervisor.Dirs` where `r.dirs()` exists. One pre-existing Low remains: a same-name install racing a trial start, between `sup.Start` staging and `versionOf`'s stat, could report the new binary's version for the old process until its next start. The old cache had the same gap. `CoreUpdater` holds the artifacts lock across an update's install and trial and across a rollback (`internal/artifacts/core.go:107-131`), so tikray never races itself into it.
